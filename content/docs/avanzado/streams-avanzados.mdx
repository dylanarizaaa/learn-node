## Backpressure

Imagina que lees un archivo a 1 GB/s y lo envías a un cliente que descarga a 1 MB/s. Si no hubiera freno, los datos se acumularían en memoria hasta agotarla. La <Term slug="backpressure">backpressure</Term> es ese freno:

- Cada stream tiene un búfer con un tamaño orientativo, `highWaterMark` (16 KiB para bytes, 16 objetos en modo objeto).
- `writable.write(chunk)` devuelve `false` cuando el búfer está lleno: **deja de escribir** hasta el evento `'drain'`.
- `pipeline` y `for await` lo gestionan por ti: el productor solo avanza cuando el consumidor pide más.

```js
// A mano (para entenderlo; en la práctica, usa pipeline)
for (const line of lines) {
  if (!res.write(line)) await once(res, 'drain'); // espera a que el cliente consuma
}
res.end();
```

## Generadores como fuente

Un generador produce valores **bajo demanda**: el siguiente no se calcula hasta que alguien lo pide. Combinado con `Readable.from`, es la forma más simple de crear un stream con backpressure:

```js
function* numbers(limit) {
  for (let i = 0; i < limit; i++) yield `${i}\n`;  // nada se calcula por adelantado
}

await pipeline(Readable.from(numbers(1e9)), createWriteStream('numeros.txt'));
```

Y como etapas intermedias de `pipeline` puedes usar **funciones generadoras asíncronas**:

```js
await pipeline(
  createReadStream('datos.csv'),
  csvParser(),
  async function* (rows) {
    for await (const { record } of rows) if (record.categoria === 'ocio') yield record;
  },
  saveToDatabase,
);
```

## De la base de datos al cliente, fila a fila

`statement.iterate()` de `node:sqlite` devuelve un iterador que lee **una fila cada vez**. Encadenado con `Readable.from`, un transform CSV y la respuesta HTTP, exportas un millón de filas con memoria constante: la base de datos avanza al ritmo de la red.

## Errores comunes

- `stream.on('data', …)` sin pausar cuando el destino va lento: ignora la backpressure.
- Acumular en un array dentro del `for await` «para luego escribirlo»: deshace la ventaja del streaming.
- No cerrar la respuesta si el pipeline falla a mitad: `pipeline` destruye todas las etapas, pero el cliente recibirá un archivo cortado (las cabeceras ya se enviaron). Avísalo en logs.
