## El problema

Quieres que **todos** los logs de una petición lleven su `requestId`, incluidos los que escribe el servicio o el repositorio. Opciones:

- Pasar `req` o el logger como parámetro a cada función: contamina capas que no deberían saber nada de HTTP.
- Una variable global: con cientos de peticiones intercaladas por el event loop, se mezclarían.

## La idea

<Term slug="asynclocalstorage">AsyncLocalStorage</Term> guarda un valor que viaja con la **cadena asíncrona**: todo lo que se ejecute dentro de `run()`, directa o indirectamente, y también después de cualquier `await`, `setTimeout` o callback, ve ese valor. Otra petición, con su propio `run()`, ve el suyo.

```js
import { AsyncLocalStorage } from 'node:async_hooks';

const context = new AsyncLocalStorage();

function logSomething() {
  console.log('petición', context.getStore()?.id); // sin parámetros
}

context.run({ id: 'A' }, async () => {
  await new Promise((r) => setTimeout(r, 10));
  logSomething(); // 'petición A'
});
context.run({ id: 'B' }, () => logSomething()); // 'petición B'
```

## Usos típicos

- Id de petición y logger con contexto.
- Id del usuario o del *tenant* para auditoría.
- Trazas distribuidas (OpenTelemetry lo usa por debajo).

## Errores comunes

- Usarlo para pasar datos de negocio entre funciones: dependencias implícitas difíciles de seguir. Resérvalo para preocupaciones transversales (logs, trazas).
- Llamar a `getStore()` fuera de cualquier `run()`: devuelve `undefined`. Ten siempre un valor por defecto.
- Iniciar el contexto después de middleware que encolan trabajo por su cuenta: inicia el `run()` lo antes posible en la cadena.
