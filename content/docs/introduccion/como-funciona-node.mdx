- **<Term slug="libuv">libuv</Term>** es una biblioteca en C que hace la entrada/salida (red, disco, temporizadores) de forma asíncrona y mantiene el **event loop**.

## Un solo hilo para JavaScript

Tu código JavaScript se ejecuta en **un único hilo**. Parece una limitación, pero es la clave del rendimiento de Node: cuando pides algo lento (leer un archivo, consultar una base de datos), Node **no espera**. Delega la operación al sistema operativo o al <Term slug="thread-pool">pool de hilos</Term> de libuv y sigue atendiendo otras cosas. Cuando el resultado está listo, el <Term slug="event-loop">event loop</Term> ejecuta tu callback.

## Lo que sí bloquea

El modelo funciona mientras cada trozo de JavaScript termine rápido. Si un callback se pone a **calcular** durante 2 segundos, nadie más es atendido durante esos 2 segundos:

```js title="bloqueo.js"
import { createServer } from 'node:http';

createServer((req, res) => {
  if (req.url === '/lento') {
    const end = Date.now() + 2000;
    while (Date.now() < end) {} // ⛔ bucle que acapara el único hilo
  }
  res.end('hola\n');
}).listen(3000);
```

Si alguien pide `/lento`, cualquier otra petición a `/` tendrá que esperar. Los culpables típicos: bucles enormes, `JSON.parse` de archivos gigantes, expresiones regulares mal escritas y las funciones `*Sync` (`readFileSync`) dentro de un servidor.

<Callout type="info" title="¿Y si necesito calcular?">
Para trabajo de CPU existen los [worker threads](/docs/avanzado/worker-threads) (otros hilos con su propio event loop) y, para aprovechar varios núcleos, el [módulo cluster](/docs/avanzado/cluster). Los usarás en Monedero en el hito 9.
</Callout>

## Resumen

- JavaScript corre en un hilo; la E/S ocurre en segundo plano.
- El event loop ejecuta callbacks cuando sus operaciones terminan.
- Bloquear el hilo con cálculo pesado bloquea a todos.

En [El event loop](/docs/nucleo/event-loop) verás el orden exacto en que se ejecutan temporizadores, promesas y E/S.
