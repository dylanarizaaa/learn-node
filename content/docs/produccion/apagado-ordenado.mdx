## La idea

En cada despliegue, la plataforma (Docker, Kubernetes, systemd, tu PaaS) envía **SIGTERM** al proceso antiguo y, si no termina en unos segundos, lo mata con SIGKILL. Si tu servidor simplemente muere, las peticiones a medias fallan y una escritura puede quedarse a medio hacer. El <Term slug="graceful-shutdown">apagado ordenado</Term>:

## Las piezas en Node

- `process.once('SIGTERM', handler)`: escuchar la señal (una vez: una segunda señal no debe reiniciar el proceso de cierre).
- `server.close(callback)`: deja de aceptar conexiones y llama al callback cuando se cierran las que hay.
- `server.closeIdleConnections()`: cierra las conexiones *keep-alive* que no están atendiendo ninguna petición (si no, `close` las esperaría).
- Las conexiones **largas** (SSE, WebSocket) nunca terminan solas: avisa a quien las gestiona para que las cierre.
- Un **temporizador de seguridad** con `unref()`: si algo se queda colgado, sal igualmente.

## Errores excepcionales

Un error que nadie capturó (`uncaughtException`) deja el proceso en un estado desconocido. Lo correcto es **registrarlo y salir** con código distinto de 0; el orquestador arrancará un proceso limpio. Intentar «seguir como si nada» lleva a errores más raros después.

## Errores comunes

- Arrancar con `npm start` en Docker: npm no siempre reenvía las señales al proceso de Node. Usa `CMD ["node", "src/server.js"]`.
- Llamar a `process.exit()` nada más recibir la señal: cortas las peticiones en curso.
- Olvidar cerrar la base de datos: en SQLite, el archivo WAL queda sin integrar hasta el siguiente arranque.

```console
{"level":30,…,"msg":"Servidor cerrado"}
```

Los tests usan la misma idea en `close()` del ayudante: emiten `shutdown`, cierran el servidor y la base de datos. Si alguna vez un test «no termina», casi siempre es una conexión o un temporizador que nadie cerró.
