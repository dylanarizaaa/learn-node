## La idea

Un test unitario prueba una función aislada. Un **test de integración** prueba varias piezas juntas: en una API, la petición HTTP real atravesando middleware, validación, servicio, repositorio y base de datos. Es el test que más confianza da, porque usa la aplicación como la usará un cliente.

Para que sean rápidos y fiables, cada test (o grupo de tests) necesita:

1. **Una base de datos propia y limpia**: con SQLite, `':memory:'`; con PostgreSQL, una base de datos de pruebas o transacciones que se deshacen.
2. **Un puerto libre**: `listen(0)` pide al sistema operativo un puerto cualquiera; después lo lees con `server.address().port`.
3. **Cerrar todo al terminar** (`after`): servidor y base de datos. Si algo queda abierto, el proceso del test no termina.

<Callout type="info" title="¿Y supertest?">
Es la librería clásica para esto. Con `fetch` global y `listen(0)` ya no hace falta: el ayudante de abajo hace lo mismo en 70 líneas, y sabes exactamente qué hace.
</Callout>

## Por qué `createApp` recibe sus dependencias

Aquí se cobra la decisión del hito 5: como `createApp({ config, db, logger })` no lee variables de entorno ni abre la base de datos por su cuenta, el test puede construir una aplicación **idéntica a la real** con una base de datos en memoria, un logger silencioso y un secreto de pruebas.

## Errores comunes

- Compartir una base de datos entre archivos de test: resultados distintos según el orden de ejecución.
- Tests que dependen de la fecha actual sin fijarla (un test del «mes actual» que falla el día 1).
- Comprobar solo el código de estado: comprueba también el cuerpo, al menos los campos importantes.
