## La idea

En tu máquina, `console.log('Gasto creado', id)` es suficiente. En producción, con miles de peticiones por minuto, necesitas **buscar y filtrar**: «todos los errores de la petición `a7b7…`», «peticiones de más de 500 ms». Para eso los logs deben ser **estructurados**: una línea JSON por evento, con campos.

```json
{"level":30,"time":1795325492411,"requestId":"c157…","method":"POST","url":"/api/expenses","status":201,"ms":6,"msg":"petición atendida"}
```

## pino

`pino` es el logger más usado en Node por su rendimiento: escribe JSON y deja el formateo a herramientas externas.

```js
import pino from 'pino';

const logger = pino({ level: process.env.LOG_LEVEL ?? 'info' });

logger.info('Servidor arrancado');
logger.info({ port: 3000 }, 'Escuchando');       // primero el objeto, después el mensaje
logger.error({ err: error }, 'Fallo al guardar'); // `err` serializa mensaje, tipo y traza
logger.debug('Solo si LOG_LEVEL=debug');

const log = logger.child({ requestId: 'a7b7' });  // todo lo que registre incluye requestId
```

Niveles, de menos a más grave: `trace`, `debug`, `info`, `warn`, `error`, `fatal`. En producción se suele usar `info`; en los tests, `silent`.

Para leerlos cómodamente en desarrollo, `pino-pretty` los colorea (como devDependency: en producción se queda en JSON).

## Qué registrar y qué no

- **Sí**: cada petición (método, ruta, estado, duración, id), errores con su traza, eventos de negocio importantes, arranque y parada.
- **Nunca**: contraseñas, tokens, cabeceras `Authorization`, datos de tarjetas, documentos de identidad. pino tiene la opción `redact` para tachar rutas concretas por si acaso.

## Errores comunes

- Concatenar datos en el mensaje (`'Usuario ' + id + ' creó…'`): no se puede filtrar por campo. Pasa un objeto.
- Registrar errores esperados (un 404, una validación fallida) como `error`: llenan las alertas de ruido. Son `info` o `warn`, o nada.
- `console.log` dentro de bucles calientes: en un servidor con carga, escribir en la consola de forma síncrona penaliza.

Sustituye el `requestLogger` del hito 5 por un middleware que asigna a cada petición un **id** (o reutiliza el del proxy en `X-Request-Id`), crea un logger hijo con él y lo deja en `req.log`. Versión del hito 8; en [AsyncLocalStorage](/docs/avanzado/async-local-storage) le añadirás una línea:

```js title="src/middleware/request-context.js"
import { randomUUID } from 'node:crypto';

const VALID_ID = /^[\w-]{1,64}$/;

export function requestContextMiddleware(logger) {
  return (req, res, next) => {
    const incoming = req.get('x-request-id');
    const requestId = incoming && VALID_ID.test(incoming) ? incoming : randomUUID();
    const log = logger.child({ requestId });
    const start = performance.now();

    req.log = log;
    res.set('X-Request-Id', requestId);
    res.on('finish', () => {
      log.info(
        { method: req.method, url: req.originalUrl, status: res.statusCode, ms: Math.round(performance.now() - start) },
        'petición atendida',
      );
    });
    next();
  };
}
```

El id que llega de fuera se valida: aceptar cualquier texto permitiría inyectar líneas falsas en los logs.

```js title="src/app.js"
app.use(requestLogger); // [!code --]
app.use(requestContextMiddleware(logger)); // [!code ++]
```

```js title="src/server.js"
import { createLogger } from './lib/logger.js'; // [!code ++]
const logger = createLogger({ level: process.env.LOG_LEVEL ?? 'info', pretty: process.env.NODE_ENV === 'development' }); // [!code ++]
const app = createApp({ db, logger }); // [!code ++]
```
